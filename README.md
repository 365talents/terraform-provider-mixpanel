# Terraform Provider for Mixpanel

Terraform provider to manage [Mixpanel](https://mixpanel.com) projects and service accounts, built on the [Terraform Plugin Framework](https://github.com/hashicorp/terraform-plugin-framework). Published on the Terraform Registry as [`365talents/mixpanel`](https://registry.terraform.io/providers/365talents/mixpanel).

## Resources and data sources

| Name | Description |
|---|---|
| [`mixpanel_project`](docs/resources/project.md) | Project (name, domain, timezone). Destroying it only removes it from the state, see [Acceptance tests](#acceptance-tests). |
| [`mixpanel_service_account`](docs/resources/service_account.md) | Organization service account |
| [`mixpanel_service_account_project_membership`](docs/resources/service_account_project_membership.md) | Role of a service account in a project |
| [`mixpanel_project` (data source)](docs/data-sources/project.md) | Look up a project by name |

## Usage

```terraform
terraform {
  required_providers {
    mixpanel = {
      source = "365talents/mixpanel"
    }
  }
}

provider "mixpanel" {
  service_account_username = "foo.mp-service-account"
  # service_account_secret: prefer the MIXPANEL_SERVICE_ACCOUNT_SECRET environment variable
}

resource "mixpanel_project" "myproject" {
  name     = "myproject"
  domain   = "EU"
  timezone = "Europe/Paris"
}

resource "mixpanel_service_account" "backend" {
  username = "backend-production"
}

resource "mixpanel_service_account_project_membership" "backend" {
  service_account_id = mixpanel_service_account.backend.id
  project_id         = mixpanel_project.myproject.id
  role               = "consumer"
}
```

The provider authenticates with a Mixpanel service account with the **Admin** organization role. Credentials can also be set with the `MIXPANEL_SERVICE_ACCOUNT_USERNAME` and `MIXPANEL_SERVICE_ACCOUNT_SECRET` environment variables. See [docs/index.md](docs/index.md) for all provider options.

## Requirements

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.0
- [Go](https://golang.org/doc/install) >= 1.26 (to build the provider)

## Developing the provider

```shell
go install          # build the provider into $GOPATH/bin
go test ./...       # unit tests
go generate ./...   # regenerate docs/ from the schemas and examples/
```

Docs in `docs/` are generated by [tfplugindocs](https://github.com/hashicorp/terraform-plugin-docs): edit the schema descriptions or `examples/`, then run `go generate ./...`. CI fails if the generated docs are out of date.

Releases are built by GoReleaser (`.github/workflows/release.yml`) when a `v*` tag is pushed.

## Acceptance tests

Acceptance tests run against the real Mixpanel API. Each test creates what it needs (service accounts, memberships, ...) and deletes it at the end. If a run is interrupted, delete the leftover `tf-acc-*` resources by hand in the Mixpanel organization settings.

Projects are the exception: only owners can delete them, and service accounts can be at most admin, so the provider can't delete a project. The tests use a persistent test project instead, that they import. Destroying a `mixpanel_project` only removes it from the state, so the project is kept. The tests rename it and set the name back at the end.

Acceptance tests only run when `TF_ACC` is set (`make testacc` sets it), and then fail if one of the variables below is missing.

### Service account

Create a dedicated service account in Mixpanel, under **Organization Settings > Service Accounts**, with the **Admin** organization role. Admin is needed to create projects and manage service accounts.

Use a test organization if you have one: the tests create real resources.

### Test project

Create a project for the tests in Mixpanel, for example `tf-acc`, and keep it. Any domain and timezone work. Add the service account above to it with the **Admin** role.

### Environment variables

| Variable | Description |
|---|---|
| `MIXPANEL_SERVICE_ACCOUNT_USERNAME` | Username of the service account above |
| `MIXPANEL_SERVICE_ACCOUNT_SECRET` | Secret of the service account above |
| `MIXPANEL_TEST_PROJECT_ID` | Id of the test project above |

Locally:

```shell
export MIXPANEL_SERVICE_ACCOUNT_USERNAME=...
export MIXPANEL_SERVICE_ACCOUNT_SECRET=...
export MIXPANEL_TEST_PROJECT_ID=...
make testacc
```

In CI, add them as repository secrets (**Settings > Secrets and variables > Actions**) with the same names. `.github/workflows/test.yml` passes them to the tests. Workflows triggered from forks don't get the secrets, so the tests fail there.

*Note:* Acceptance tests create real resources, and often cost money to run.
